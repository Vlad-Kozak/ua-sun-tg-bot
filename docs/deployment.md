# Розгортання на власному сервері

Покроково: від створення бота в BotFather до працюючого `@all` у групі.
Основний варіант — Docker Compose. Варіант без Docker описаний [нижче](#варіант-без-docker-systemd).

---

## Що потрібно

- Linux-сервер (будь-який VPS, вистачить 512 МБ RAM)
- Docker 20.10+ і Docker Compose v2 (`docker compose`, не `docker-compose`)
- Доступ до Telegram з сервера

Домен, TLS-сертифікат і відкриті порти **не потрібні** — бот працює через long
polling і сам ходить до Telegram. Вхідних з'єднань не приймає взагалі.

---

## Крок 1. Створити бота в BotFather

У Telegram напишіть [@BotFather](https://t.me/BotFather):

```
/newbot
```

Введіть назву й username. У відповідь прийде токен виду
`123456789:AAE...` — це весь секрет проєкту, поводьтеся з ним як з паролем.

### Обов'язково: вимкнути privacy mode

```
/setprivacy
```
→ оберіть свого бота → **Disable**

Це критично. З увімкненим privacy mode Telegram показує боту **лише команди**,
тож він ніколи не побачить звичайні повідомлення і не збере список учасників для
`@all`. Детальніше — в [architecture.md](architecture.md#звідки-береться-список-учасників).

> Якщо ви вимкнули privacy mode **після** того, як додали бота в групу, — видаліть
> бота з групи і додайте заново. Інакше зміна не застосується до цієї групи.

---

## Крок 2. Викласти код на сервер

```bash
sudo mkdir -p /app/ua-sun-tg-bot
sudo chown "$USER" /app/ua-sun-tg-bot
git clone <адреса-репозиторію> /app/ua-sun-tg-bot
cd /app/ua-sun-tg-bot
```

---

## Крок 3. Налаштувати .env

```bash
cp .env.example .env
nano .env
```

Обов'язкове поле одне:

```ini
BOT_TOKEN=123456789:AAE...
```

Решта має робочі значення за замовчуванням. Повний перелік — [нижче](#змінні-оточення).

```bash
chmod 600 .env    # у файлі лежить токен
```

---

## Крок 4. Підготувати теку даних

Контейнер працює під непривілейованим користувачем з `uid=1000`, тому теку під
базу треба віддати саме йому:

```bash
mkdir -p data
sudo chown -R 1000:1000 data
```

Якщо цього не зробити, бот впаде на старті з помилкою `unable to open database file`.

---

## Крок 5. Запуск

```bash
docker compose up -d --build
docker compose logs -f
```

В логах має з'явитися:

```
Застосовую міграції…
INFO  [alembic.runtime.migration] Running upgrade  -> f97694849192, initial schema
INFO  bot.db.session: Підключення до БД ініціалізовано
INFO  __main__: Стартуємо як @your_bot (id=123456789)
INFO  aiogram.dispatcher: Start polling
```

Якщо натомість бачите `Telegram відхилив BOT_TOKEN` — перевірте токен у `.env`.

Якщо бачите попередження `Privacy mode увімкнено` — поверніться до кроку 1.

Міграції схеми БД застосовуються автоматично при кожному старті, окремих дій не потрібно.

---

## Крок 6. Додати бота в групу

1. Додайте бота в групу.
2. **Зробіть його адміністратором.** Мінімально достатньо права «Видаляти
   повідомлення» — конкретні права не важливі, важливий сам статус адміна:
   лише адмінам Telegram надсилає події `chat_member` про вхід і вихід людей.
   Без цього бот дізнаватиметься про вихід учасників із затримкою.
3. Бот сам надішле привітання з інструкцією.

Перевірка:

```
/stats      — скільки людей бот уже знає
@all        — має покликати всіх відомих
```

На старті база порожня — це нормально. Бот запам'ятовує людей, коли вони пишуть
у чат, тож за день-два активності список стає повним.

## Змінні оточення

| Змінна | За замовчуванням | Призначення |
|---|---|---|
| `BOT_TOKEN` | — | **Обов'язкова.** Токен від BotFather |
| `DATABASE_URL` | `sqlite+aiosqlite:///data/bot.db` | Шлях до БД. У compose перевизначається |
| `LOG_LEVEL` | `INFO` | `DEBUG` \| `INFO` \| `WARNING` \| `ERROR` |
| `HEARTBEAT_FILE` | `data/heartbeat` | Файл-мітка для healthcheck |
| `OWNER_IDS` | порожньо | Зарезервовано, поточна логіка не використовує |
| `MENTION_BATCH_SIZE` | `6` | Скільки згадок в одному повідомленні |
| `MENTION_BATCH_DELAY` | `0.35` | Пауза між батчами, секунд |
| `DEFAULT_ALL_POLICY` | `admins` | Хто може кликати `@all` у нових чатах |
| `DEFAULT_TAG_POLICY` | `admins` | Хто може редагувати теги в нових чатах |
| `DEFAULT_COOLDOWN_SECONDS` | `600` | Пауза між викликами тега |
| `DEFAULT_TIMEZONE` | `Europe/Kyiv` | Таймзона для тихих годин |
| `DEFAULT_QUIET_HOURS_ENABLED` | `true` | Вмикати тихі години в нових чатах |
| `DEFAULT_QUIET_START` / `_END` | `23` / `8` | Межі тихих годин |

`DEFAULT_*` — це саме **дефолти для нових чатів**. Уже доданий чат ними не
керується: він має власні налаштування, які змінюються командою `/settings`
(див. [usage.md](usage.md#налаштування-чату)). Зміна `.env` не переписує
налаштування наявних чатів.

## Щоденна експлуатація

### Оновлення

```bash
cd /app/ua-sun-tg-bot
git pull
docker compose up -d --build
```

Міграції накотяться самі. Простій — кілька секунд.

### Логи

```bash
docker compose logs -f --tail 100
```

Логи обмежені 10 МБ × 5 файлів, диск не заб'ють.

### Чи живий бот

```bash
docker compose ps
```

Колонка `STATUS` показує `healthy` або `unhealthy`. Це не те саме, що «процес
запущений»: бот раз на 30 секунд оновлює файл-мітку `data/heartbeat`, і
healthcheck перевіряє її свіжість. `unhealthy` означає, що контейнер живий, але
цикл обробки апдейтів став — привід подивитися логи.

Перевірити вручну:

```bash
docker compose exec bot python /usr/local/bin/healthcheck.py
```

### Перезапуск і зупинка

```bash
docker compose restart
docker compose down          # зупинити
docker compose up -d         # підняти
```

`restart: unless-stopped` означає, що бот сам підніметься після ребуту сервера.

## Бекапи

Уся база — один файл `data/bot.db`. Копіювати його через `cp` під час роботи
бота **не можна**: можна отримати побитий знімок. Використовуйте скрипт, який
робить коректний гарячий бекап:

```bash
./deploy/backup.sh
```

Результат — `backups/bot-РРРРММДД-ГГХХСС.db.gz`. Бекапи, старші за 14 днів,
видаляються автоматично.

Cron щодня о 4:00:

```bash
crontab -e
```
```
0 4 * * * /app/ua-sun-tg-bot/deploy/backup.sh >> /var/log/ua-sun-backup.log 2>&1
```

Налаштування скрипта через змінні: `DB_PATH`, `BACKUP_DIR`, `KEEP_DAYS`.

### Відновлення

```bash
docker compose down
gunzip -c backups/bot-20260726-040000.db.gz > data/bot.db
sudo chown 1000:1000 data/bot.db
docker compose up -d
```

## Варіант без Docker (systemd)

Потрібен Python 3.10+ (рекомендовано 3.12; код лишається сумісним з 3.9).

```bash
sudo useradd --system --home /app/ua-sun-tg-bot uasunbot

cd /app/ua-sun-tg-bot
python3.12 -m venv .venv
.venv/bin/pip install -e .

cp .env.example .env
nano .env                    # вписати BOT_TOKEN
chmod 600 .env

mkdir -p data
sudo chown -R uasunbot:uasunbot /app/ua-sun-tg-bot

sudo cp deploy/ua-sun-tg-bot.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now ua-sun-tg-bot
```

Перевірка:

```bash
systemctl status ua-sun-tg-bot
journalctl -u ua-sun-tg-bot -f
```

Unit розрахований на код у `/app/ua-sun-tg-bot` під користувачем `uasunbot`.
Якщо у вас інші шляхи — поправте `WorkingDirectory`, `ExecStart` і `ReadWritePaths`.

Міграції в цьому варіанті виконує `ExecStartPre` перед кожним запуском.

## Типові проблеми

| Симптом | Причина й що робити |
|---|---|
| `Telegram відхилив BOT_TOKEN` | Неправильний або зайвий пробіл у `BOT_TOKEN`. Перевірте через `/mybots` у BotFather |
| `unable to open database file` | Тека `data/` належить не тому користувачу. `sudo chown -R 1000:1000 data` |
| `@all` кличе 2–3 людей із 50 | Нормально на старті — база наповнюється поступово. Якщо не росте днями, майже напевно увімкнений privacy mode |
| Бот мовчить на `@all`, реагує на `/tags` | Класична ознака privacy mode: команди видно, звичайний текст — ні |
| Бот не реагує взагалі | `docker compose logs`. Якщо `Start polling` є, а реакції немає — перевірте, що бот не заглушений у налаштуваннях групи |
| Люди, що вийшли, досі в `@all` | Бот не адмін, тому не отримує події `chat_member`. Зробіть адміном |
| `@all` мовчки ігнорується | Спрацював cooldown або політика «лише адміни». Бот відповідає тихою реплаєм із поясненням — перевірте його |
| Після переходу групи в супергрупу зникли теги | Не мало статися: перенесення обробляється автоматично. Перевірте логи на `Перенесено дані чату` |
| У логах `TOPIC_CLOSED`, `CHAT_WRITE_FORBIDDEN` | Не помилка бота: тему форуму закрито або бракує прав на запис. Бот це переживає й пише лише рядок у лог |
| `Conflict: terminated by other getUpdates` | З токеном працює **другий екземпляр**. Див. [окремий розділ](#конфлікт-getupdates-два-екземпляри-бота) |
| `Бот уже запущений (pid=…)` | Спрацював захист від подвійного запуску — це очікувано, а не збій. Зупиніть зайву копію |
| `docker compose ps` показує `unhealthy` | Процес живий, але обробка апдейтів стала. Дивіться логи; `restart: unless-stopped` підніме контейнер, якщо процес усе ж упаде |

### Конфлікт getUpdates: два екземпляри бота

```
TelegramConflictError: Conflict: terminated by other getUpdates request;
make sure that only one bot instance is running
```

Telegram дозволяє забирати апдейти лише одному отримувачу. Якщо запущено дві
копії з тим самим токеном, апдейти дістаються то одній, то іншій — і бот
виглядає мертвим, хоча обидві копії живі.

**Токен має бути рівно в одного процесу.** Найчастіші причини:

| Причина | Як перевірити |
|---|---|
| Старий контейнер не зупинили | `docker ps -a \| grep ua-sun` |
| Другий compose-проєкт із того ж коду | `docker ps --format '{{.Names}}\t{{.Image}}'` |
| Бот запущений ще й через systemd | `systemctl status ua-sun-tg-bot` |
| Локальний процес для налагодження | `ps aux \| grep "python -m bot"` |
| Копія на іншому сервері | той самий `.env` на другій машині |
| Налаштований webhook | конфліктує з polling; бот знімає його сам при старті |

**Діагностика однією командою.** Зупиніть бота й запустіть скрипт — він опитає
Telegram і огляне цю машину:

```bash
docker compose down
python3 deploy/diagnose.py
```

Скрипт нічого не змінює, залежностей не потребує. Він показує: чи валідний
токен, чи не налаштований webhook, чи тримає хтось `getUpdates` просто зараз,
і що зі схожого запущено на цьому сервері (контейнери, процеси, systemd).

Код повернення: `0` — токен вільний, `1` — зайнятий іншим екземпляром,
`2` — не вдалося визначити.

Те саме вручну, якщо скрипт недоступний:

```bash
curl -s "https://api.telegram.org/bot<ВАШ_ТОКЕН>/getUpdates?timeout=0&limit=1" | head -c 300
```

| Відповідь | Висновок |
|---|---|
| `"ok":true` | На цьому сервері чисто — конфлікт створювали власні контейнери, просто підніміть один |
| `"error_code":409` | Копія працює **деінде** — інший сервер або процес поза Docker |

**Якщо копію знайти не вдається** — є гарантований спосіб обірвати їй доступ:
@BotFather → `/mybots` → ваш бот → **API Token** → **Revoke current token**.
Старий токен миттєво стає недійсним, чужа копія відвалюється. Впишіть новий
токен у `.env` і перезапустіть бота. Дані в базі від цього не постраждають.

Ще одна підказка є в самих логах: бот пише свій відбиток при старті
(`Екземпляр: host=… pid=… data=…`), а до повідомлення про конфлікт додає
рядок про те, що блокування тримає саме він — отже, друга копія поза цією текою.

Прибрати зайве:

```bash
docker compose down                   # зупинити все з цього compose
docker ps -a | grep ua-sun-tg-bot     # переконатися, що нічого не лишилось
docker rm -f <id зайвого контейнера>
docker compose up -d
```

Якщо друга копія була на іншій машині або під systemd — зупиніть її там:

```bash
sudo systemctl stop ua-sun-tg-bot && sudo systemctl disable ua-sun-tg-bot
```

**Що робить бот сам:**

- при старті бере блокування `data/bot.lock` — друга копія **на тому самому
  сервері з тією ж текою даних** просто не запуститься й напише про це в лог;
- знімає webhook перед polling, бо він мовчки конфліктує з `getUpdates`;
- згортає потік однакових повідомлень про конфлікт до одного зрозумілого рядка
  раз на хвилину, замість ERROR кожні 5 секунд.

Блокування не рятує лише від копії на **іншій** машині або з іншою текою даних —
там допоможе тільки зупинити зайвий процес.

### Діагностика зсередини контейнера

```bash
docker compose exec bot python -c "
import sqlite3
con = sqlite3.connect('data/bot.db')
for table in ('chats','users','chat_members','tags','tag_members'):
    print(table, con.execute(f'select count(*) from {table}').fetchone()[0])
"
```
